# Firestore 安全規則檢查結果

## 原本規則的風險

| # | 原本的規則 | 風險 |
|---|---|---|
| 1 | `tenants` 任何登入者都可 `create`（只要 ownerId 寫自己） | 任何人可無限建立租戶與 Owner 身分，灌爆資料庫、拉高費用 |
| 2 | `invitedSigningUpdate` 允許受邀者直接 `update` 合約 | 受邀者可繞過後端，直接修改合約文件的其他欄位（例如狀態、簽名紀錄） |
| 3 | `invitedParty` 以 Email 比對讀取合約 | 使用匿名登入時沒有 Email，這條沒有作用；未來改 Email 登入時，任何能登入該 Email 的人都能讀整份合約 |
| 4 | `signatureInvites` 沒有明確規則 | 目前預設拒絕（安全），但沒有寫明，容易在日後修改時誤開 |

## 新規則（`firestore.rules`）

網站前端**完全不直接讀寫 Firestore**，所有合約、簽署、文件、PDF 都經由後端 API（Cloud Functions）檢查「已登入」與「是合約建立者」或「持有效一次性簽署連結」後才存取。後端使用 Admin SDK，不受規則限制。

因此規則改為：**除了使用者自己的 `users/{uid}` 文件外，前端直接存取一律拒絕。** 即使有人拿到網站公開的 Firebase API Key，也讀不到任何合約資料。

## 模擬器實測（9/9 通過）

| 測試 | 結果 |
|---|---|
| 讀別人的租戶 | 拒絕 403 |
| 讀別人的合約 | 拒絕 403 |
| 列出合約 | 拒絕 403 |
| 讀簽署邀請（含加密 Token） | 拒絕 403 |
| 未登入讀合約 | 拒絕 403 |
| 自建租戶 | 拒絕 403 |
| 竄改合約狀態為已簽署 | 拒絕 403 |
| collection group 查詢所有簽署邀請 | 拒絕 403 |
| 寫自己的 users 文件 | 允許 200 |

後端 API 另有 59 項流程測試，包含「其他使用者看不到、改不了、下載不到我的合約」。

## 部署

`deploy.cmd` 會一起部署規則（`firestore:rules`）。部署後可到 Firebase 主控台 → Firestore → 規則，確認內容與 `firestore.rules` 相同。
